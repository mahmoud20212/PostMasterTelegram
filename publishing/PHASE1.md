# المرحلة الأولى: سلامة جلسات النشر

## التغييرات

- `models.py` و`migrations/0007_publishingrun.py`: جدول إضافي `PublishingRun` به UUID، حساب ثابت، حالة النشاط، claim للتنفيذ، وأوقات البدء والإيقاف. قيد جزئي فريد يمنع أكثر من run نشطة للمستخدم. لا حذف أو تعديل لسجلات المستخدمين الحالية في migration.
- `services/runs.py`: Start بمعاملة تبدأ بـ conditional UPDATE على المستخدم، ثم إنشاء run. Stop يبطل run؛ cleanup الخاص بمهمة قديمة لا يوقف run أحدث. أول statement في معاملات انتقال الحالة كتابة، ولا نعتمد على `select_for_update()` في SQLite.
- `services/engine.py`: جميع فحوص الحلقة والانتظار وتحديث المؤشرات مرتبطة بـ run ID. الحساب ثابت خلال التشغيل؛ تغيير اختياره يسري في التشغيل التالي. إعادة فحص المستخدم والاشتراك والحساب والجلسة والمجموعة والرسالة حول حجز الحصة وقبل الإرسال. المجموعات المؤهلة `pending` و`active` فقط. المهام ترفض الاشتراك المنتهي دون تنفيذ عملية حذف بيانات الاشتراك من داخل sender قديم.
- `tasks.py`: تمرير run ID. الرسائل القديمة بلا ID لا تنشر؛ لا يجوز إسنادها إلى run جديدة.
- `test_session_safety.py`: اختبارات مع Telegram mocks، ومنها Start متزامن عبر اتصالين مستقلين بقاعدة البيانات، Stop ثم Start، تثبيت الحساب، استقلال المستخدمين، وفشل broker/configuration/connect.
- `config/test_settings.py`: SQLite مؤقتة على القرص لاختبار تنافس الاتصالات، مع إعدادات اختبار فقط. لا تتصل بقاعدة التطبيق.

لا تغيير للـ pool أو Dispatcher أو dependencies أو إعدادات الإنتاج. الأوامر والأزرار الحالية كما هي.

## التحقق المحلي

من جذر المستودع، باستخدام البيئة الموجودة:

```powershell
.\.venv\Scripts\python.exe -B manage.py test --settings=config.test_settings --verbosity=1
.\.venv\Scripts\python.exe -B manage.py check --settings=config.test_settings
.\.venv\Scripts\python.exe -B manage.py makemigrations --check --dry-run --settings=config.test_settings
git diff --check
```

تشغّل الاختبارات migrations داخل قاعدة مؤقتة فقط؛ لا ترسل رسائل Telegram ولا تحتاج Redis. الاختبارات المتزامنة لا تثبت أداء Celery أو تعدد المستخدمين تحت `solo`.

## حدود المرحلة

- لا تزال task طويلة العمر. `solo` ينفذ جلسة واحدة في كل مرة؛ هذه المرحلة تحمي الملكية ولا تعالج اختناق قدرة التنفيذ.
- SQLite تسلسل الكتابة على مستوى قاعدة البيانات، ولا توفر row locks لـ `select_for_update()`. الحماية الجديدة للـ Start تعتمد على conditional UPDATE وقيد فريد، لكن ضغط الكتابة قد ينتهي بـ `database is locked`. لم تتغير آلية الحصة اليومية القديمة؛ لا يوجد ضمان جديد لدقتها تحت تنافس العمليات. لا تعتبر نجاح اختبار اتصالين إثباتاً لقابلية التوسع.
- لا توجد transaction موزعة بين DB وTelegram. Stop أو انتهاء الاشتراك بعد آخر فحص لا يستطيع سحب طلب شبكة بدأ بالفعل. لا يوجد ضمان exactly-once أو منع تكرار رسائل قبلها Telegram دون وصول الرد.
- claim تمنع تكرار تنفيذ نفس run. القتل القسري للعملية أو فقد broker بعد حفظ Start وقبل enqueue قد يترك run نشطة دون تنفيذ. لا يوجد heartbeat أو استرداد تلقائي أو Dispatcher؛ يتوفر أمر استرداد إداري في Phase 1.1 كما هو موضح أدناه. لا تعِد إرسال task لنفس run لتجاوز claim.
- cleanup يغطي الأخطاء العادية والإلغاء، بما فيها decrypt/connect/disconnect، لكنه لا يستطيع ضمان الكتابة عند تعطل قاعدة البيانات أو قتل العملية قسرياً.
- FloodWait يُرفع إلى المعالج بدلاً من الانتظار التلقائي في Telethon؛ الاستئناف الآلي بعده وتخزين cooldowns ليسا ضمن المرحلة.
- لم تُصلح معادلة السكون أو تُفعّل سجلات Delivery الدائمة؛ تبقيان عملاً لاحقاً.

## النشر الآمن — خطوات للمشغّل، لم تُنفذ تلقائياً

1. اختبر الإصدار في بيئة معزولة. احفظ نسخة متسقة من SQLite ونسخة إصدار التطبيق قبل النشر؛ احمِ النسخة لأنها تحتوي بيانات sessions مشفرة. لا تنسخ قاعدة قيد الكتابة نسخاً غير متسق.
2. أوقف النشر للمستخدمين عبر Stop في الإصدار الحالي، وانتظر خروج المهام، ثم أوقف bot وWorker وBeat لمنع Start جديدة. تأكد من عدم بقاء Worker قديمة؛ فهي لا تعرف run IDs. إذا كانت حالة مستخدم عالقة بسبب crash، سوّها بإجراء Stop إداري قبل استئناف الخدمة.
3. انشر الكود المتوافق لكل من bot وWorker معاً. باستخدام إعدادات البيئة الفعلية نفذ `python manage.py migrate --plan` وراجع الخطة، ثم `python manage.py migrate` و`python manage.py check`. الـ migration الجديدة الخاصة بهذه المرحلة هي `publishing.0007_publishingrun`.
4. شغّل الخدمات بنفس إعداد pool الحالي. رسائل النشر القديمة المنتظرة بلا run ID تصبح no-op؛ لذلك أعد تشغيل جلسات المستخدمين عبر Start الجديدة. لا تنفذ purge عامة قد تحذف مهام خدمات أخرى.
5. تحقق من مستخدم تجريبي مخوّل: run واحدة، Stop ثم Start يولدان UUID مختلفين، وتغيير الحساب لا يغيّر حساب run الجارية. راقب أخطاء DB وحالة Worker. تبقى قيود `solo` كما هي.

للرجوع، اتبع إجراء Phase 1.1 أدناه؛ إيقاف الجلسات وحده لا يزيل الرسائل ذات الوسيطين من broker. يمكن إبقاء الجدول الإضافي دون حذف migration أو records. الرجوع للكود السابق يعيد أيضاً عيوبه المعروفة.

## Phase 1.1: إصلاحات الجاهزية

- نُقل نشر Celery إلى `sync_to_async(..., thread_sensitive=False)` حتى لا يحجز thread الخاصة بعمليات DB وStop. أضيفت مهلة اتصال وsocket قدرها 3 ثوانٍ ومحاولة إضافية واحدة للنشر. هذه حدود لعمليات الشبكة والمحاولات وليست ضمان مهلة كلية ثابتة، خصوصاً مع DNS أو انتظار producer pool. لا نستخدم timeout على coroutine للنشر يوهم بأن thread الخلفية توقفت.
- عند فقد رد broker، يُبطل run ID نفسه. إذا وصلت task لاحقاً فإنها تفشل في claim. إذا بدأت وأرسلت فعلاً قبل الإبطال فلا يمكن سحب الرسالة، وتظل النتيجة غير مؤكدة. لا توجد إعادة enqueue تلقائية من خدمة Start؛ إعادة محاولة مكتبة Celery تحمل نفس run ID وتحميها claim.
- تعاد معاملات Start/Stop القابلة للتراجع فقط، بحد أقصى 3 محاولات وتوقف 0.05 ثم 0.1 ثانية. مهلة SQLite للاتصال تضاف إلى كل محاولة؛ الإعداد الافتراضي 5 ثوانٍ قد يعني انتظاراً يقارب 15 ثانية. أخطاء القفل المعروفة تعطي فشلاً صريحاً للمستخدم؛ لا يُعاد نشر task بسبب retry لمعاملة DB.
- cleanup يحاول إنهاء run وفصل client، ويسجل أخطاءهما منفصلة. عند وجود exception أو cancellation أصلية تُحفظ؛ وعند فشل cleanup وحده يُرفع الخطأ ولا يُعلن نجاح صامت. فصل client محدود بـ 10 ثوانٍ. لا يضمن ذلك cleanup عند قتل العملية قسرياً أو استمرار تعطل DB.
- تغيّرت `config/settings.py` لضبط حدود broker، وHandler الإيقاف ليعرض فشل الإيقاف عند contention. لم تتغير أسرار البيئة أو `--pool=solo` أو بنية مهام النشر الطويلة.

## الاسترداد الإداري للجلسات العالقة

أمر الاسترداد لا يفحص liveness تلقائياً، ولا يعيد تشغيل مهمة، ولا يصفّر `task_claimed`، ولا يحذف بيانات الحسابات والرسائل. التأكيد مسؤولية المشغّل؛ لا تشغله اعتماداً على عمر run أو غياب رد `inspect` وحده.

1. أوقف قبول Start جديدة: أوقف bot وBeat وأي منتج آخر لمهام النشر، وانتظر تأكيد خروج العمليات.
2. أوقف Worker التي يمكنها تنفيذ الجلسة. انتظر خروج العملية/container فعلياً؛ إشارة shutdown أو انتهاء مهلة inspect لا يكفيان. عند الاضطرار للقتل القسري، تحقق من خروجها ولا تفترض معرفة نتيجة آخر إرسال Telegram.
3. حدد `telegram_user_id` وUUID المستهدف من سجلات run أو قراءة جدول `PublishingRun`. استخدم UUID محددة، لا أحدث run بصورة ضمنية.
4. بعد التأكد من توقف التنفيذ القديم، نفذ باستخدام إعدادات البيئة المقصودة:

```text
python manage.py recover_publishing_run TELEGRAM_USER_ID --run-id RUN_UUID --confirm-execution-stopped
```

للمستخدم القديم الذي يحمل `is_publishing=True` دون run نشطة:

```text
python manage.py recover_publishing_run TELEGRAM_USER_ID --legacy --confirm-execution-stopped
```

الأمر يرفض التنفيذ دون التأكيد. UUID لا تخص المستخدم أو run قديمة أُبطلت لا تمس الجلسة الجديدة. وضع `--legacy` يرفض أي مستخدم لديه run نشطة. يظل claim القديم محفوظاً. إذا فشل الأمر بسبب DB، لا تستأنف النشر حتى تأكيد الحالة؛ لا توجد معالجة جماعية تلقائية.

5. شغّل الإصدار الجديد من الخدمات، ثم أعد Start للمستخدم المعني. تتولد UUID جديدة. الرسائل القديمة التي تحمل UUID المبطل لا تستطيع استعادة الملكية. قد يلزم تفريغها بالـ Worker المتوافقة لتجنب تراكم queue.

هذا الإجراء يشمل: تعطل bot قبل enqueue، وتعطل Worker بعد claim، والحالات القديمة أثناء الترقية. يفضل قبول توقف تشغيلي قصير على تشغيلين يحتمل إرسالهما معاً.

## ترتيب النشر وrollback للرسائل المنتظرة والمحجوزة

لا يدعم الإصدار القديم task ذات الوسيطين. توقف كل منتجات المهام أولاً، وامنع إطلاق Worker قديمة تلقائياً بواسطة supervisor أثناء نافذة الصيانة. لا تتراجع عن schema الإضافية.

**الترقية:** خذ backup متسقة، أوقف المنتجين والجلسات، تحقق من خروج Worker القديمة، وسوّ الحالات القديمة عند الحاجة بالأمر الإداري. طبّق migration وافحص النظام. شغّل Worker الجديدة ثم المنتجين. لا تدع Worker قديمة تستهلك مهام bot الجديدة. المهام القديمة ذات الوسيط الواحد تصبح no-op، ويُعاد Start من الواجهة عند الحاجة.

**الرجوع:**

1. أوقف bot وBeat وكل منتجي المهام، مع إبقاء كود Worker المتوافق مع وسيطين متاحاً. أوقف runs النشطة وانتظر خروج عمليات التنفيذ، أو استخدم الاسترداد الإداري بعد التأكد من خروجها.
2. استخدم Worker من الإصدار الجديد لتصريف الرسائل المتبقية قبل تشغيل أي Worker قديمة. runs المبطلَة تجعل مهام نشرها no-op. المهام غير المتعلقة بالنشر تُنفذ طبيعياً؛ لا تحذف queue أو مفاتيح Redis.
3. تحقق من الحالات الثلاث: `active` و`reserved` لدى جميع Workers، والرسائل المنتظرة في broker. تحقق أيضاً من `scheduled` ومن رسائل Redis unacknowledged المحجوزة لعمليات توقفت. راعِ كل queue وRedis priority lists التي يستهلكها التطبيق. لا يكفي `LLEN celery=0`، ولا يعد timeout لـ inspect دليلاً على الفراغ، خصوصاً مع `solo`.
4. الرسائل المحجوزة لعملية ميتة قد تعود بعد `visibility_timeout` (غير مغير هنا؛ راجع القيمة الفعلية). أبقِ مستهلكاً متوافقاً حتى تعود وتُصرّف. يجب الحصول على ردود فحص صريحة والتحقق من بيانات broker بقراءة لا تعدّلها، ثم إعادة الفحص بعد خروج Worker المتوافقة لضمان عدم إعادة رسائل محجوزة عند الإغلاق. لا تقرأ أو تطبع أجسام رسائل حساسة أثناء التشخيص.
5. **إذا تعذر إثبات تصريف رسائل الإصدار الجديد من queued/reserved/active/scheduled/unacknowledged، فلا تشغّل Worker القديمة على هذا broker. أجّل rollback وأبقِ الإصدار المتوافق حتى اكتمال المصالحة.** هذه الخطة تتطلب نافذة صيانة وتحكماً في كل المنتجين والمستهلكين؛ rollback فورية مع backlog مشتركة غير مدعومة. لا تستخدم purge عامة أو حذف Redis DB للتغلب على القيد.
6. بعد تأكيد الفراغ، أوقف كل Workers الجديدة وتحقق من عدم بقاء حجوزات، ثم أعد الإصدار القديم للـ Worker أولاً ثم المنتجين. احتفظ بجدول runs ونسخة التطبيق الجديدة وسجلات المصالحة. أي رسائل يعود إرسالها يدوياً لاحقاً يجب أن تستخدم صيغة الإصدار المستهدف.

اختبارات التوافق المحلية تثبت اختلاف التوقيع وتجاهل المهام القديمة في الغلاف الجديد، ولا تثبت تصريف Redis فعلية. يلزم تمرين هذه الخطوات على staging بنفس إصدارات Celery/Kombu/Redis قبل النشر المتحكم به.

## نطاق الاختبارات والجاهزية

أضيفت اختبارات broker المتوقف وفقد الرد، والاسترداد قبل enqueue وبعد claim، وحماية المستخدم الآخر والجلسة الجديدة، والقفل الفعلي لقاعدة SQLite المؤقتة، وrollback المعاملة قبل إعادة المحاولة، والأخطاء المركبة في cleanup، وFloodWait وSlowMode، وبيانات المستخدم القديم عبر migration.

يوجد اختبار Worker Celery حقيقية غير eager بـ `solo` في thread، وbroker/backend في الذاكرة، مع mock للمحرك. إنه يثبت وصول الرسالة إلى غلاف task؛ لا يحاكي قتل process أو Redis أو Telegram. جميع اتصالات Telegram في الاختبارات mocks.

الجاهزية المقصودة نشر متحكم به مع مشغّل وإجراء استرداد ونافذة صيانة، وليست high availability أو توسعاً متعدد المستخدمين تحت `solo`. يلزم نجاح الاختبارات وفحص إعدادات البيئة الفعلية وتمرين الترقية والرجوع على staging. لا توجد تغييرات dependencies أو Dispatcher أو PostgreSQL في هذه المرحلة.
